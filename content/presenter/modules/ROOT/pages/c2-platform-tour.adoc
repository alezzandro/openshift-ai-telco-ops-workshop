= C2. Platform tour

Time: about 15 minutes.

== GPU inventory

In the OpenShift console, **Compute → Nodes**. Filter or look for `worker-gpu`.

Each GPU node should advertise `nvidia.com/gpu` allocatable **4**.

Then in **OpenShift AI**, open **Observe & monitor → Infrastructure**. That page is the cluster accelerator view: GPU count, utilization, memory, hardware inventory, and Kueue queues (pool usage, workloads).

Talking points for the Kueue cards:

* **Cluster queue consumption** reads `ClusterQueue` objects from the API. The first load can flash `Error loading cluster queue data` / `storage is (re)initializing` (HTTP 429 while the kube-apiserver watch cache for `kueue.x-k8s.io` warms up). Wait a few seconds; it is **not** the DSCI metrics PVC. DSCI `MonitoringStackAvailable=True` is the Prometheus path.
* **Accelerator** on that widget is `nvidia.com/gpu` (integer counts). **Compute** and **memory** are Kueue flavor CPU and memory (`cpu` / `memory` on the ClusterQueue, not node utilization). Hardware profiles *do* request 4 CPU and 16Gi per replica; the dashboard often paints those bars at 0% because it does not parse Kubernetes Quantity suffixes (`24660m`, `98778Mi`) the same way it parses GPU integers. That is a UI quirk, not "Kueue is GPU-only."
* Fleet **Average compute** on the same page is cluster-wide node CPU over ~140 allocatable cores. Seven vLLM pods move that ratio a few percent, which can look like 0%. GPU cards use DCGM `accelerator_gpu_utilization` (idle models also read 0% until you send traffic).

https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5/html/managing_openshift_ai/managing-observability_managing-rhoai[Manage observability]

== Models dashboard (Deployed models)

**Observe & monitor → Dashboard → Models** (cluster-admin also sees **LLM Traffic / LLM Performance / LLM Utilization**). That is a different page from **Infrastructure**.

The **Deployed models** table and the **Model deployment** dropdown read `kserve_vllm:*` recording rules from the DSCI Thanos querier. Raw `vllm:*` is scraped; without the recording rules the table stays **No data** and you cannot pick a model. Setup puts `PrometheusRule` `kserve-vllm-recording-rules` in `redhat-ods-monitoring` (`monitoring.rhobs`).

Talking points:

* Filter **Project** to `{ran_project}` or `{core_project}`, then the **Model deployment** list. Both playground Ministrals should appear once at least one replica is Ready.
* Request / latency / TTFT charts stay near zero until someone curls the Route (P1). **No data** on the whole table is a scrape/recording-rule problem; **0** after a listed model is idle.
* CPU / namespace-quota columns often stay empty: those PromQL joins `node_namespace_pod_container:container_cpu_usage_seconds_total:sum_irate` from cluster Prometheus, which DSCI Thanos does not store.
* **LLM Traffic / Performance / Utilization** reuse `kserve_vllm:*` (TTFT, KV cache, prefix cache) and add llm-d metrics (`llm_d_epp_*`, `inference_model_request_error_total`). This lab deploys KServe `InferenceService`, not `LLMInferenceService`, so EPP/error panels can stay empty. That is expected.

https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5/html/managing_openshift_ai/managing-observability_managing-rhoai#view-model-performance-metrics_managing-rhoai[View model performance metrics (OpenShift AI 3.5)]

== CPU workbench (LangChain + vLLM)

Serving projects (`{presenter_project}`, `{ran_project}`, `{core_project}`) are Kueue-managed. The dashboard then shows **only hardware profiles that name a local queue**, so you cannot pick **CPU only** there. That is expected, not a broken profile.

Setup created a separate Data Science Project **`{workbench_project}`** with **no** LocalQueue. The CPU workbench is already running there.

. In OpenShift AI, open project `{workbench_project}` (display name *Telco Ops Notebooks*).
. Workbenches → click the name **CPU LangChain examples** (opens JupyterLab).
. In JupyterLab, open `START-HERE.md`, then
  `llm-on-openshift/examples/notebooks/langchain/Langchain-vLLM-Prompt-memory.ipynb`.

That notebook is from the Red Hat AIS examples repository
https://github.com/rh-aiservices-bu/llm-on-openshift/blob/main/examples/notebooks/langchain/Langchain-vLLM-Prompt-memory.ipynb[Langchain-vLLM-Prompt-memory.ipynb].
Setup cloned the repo onto the workbench PVC.

Talking points:

* A workbench is a Kubeflow `Notebook`. OpenShift AI 3.5 exposes it through the shared data-science gateway (same OpenShift identity as the console).
* This one requests **CPU and memory only** (`cpu-only` HardwareProfile). It schedules on general workers, not on the tainted GPU node.
* After C3, change `inference_server_url` to the in-cluster predictor Service in `{presenter_project}` (`http://<predictor>.{presenter_project}.svc.cluster.local:8080`). KServe Standard Services are headless — use container port 8080, not Service port 80. Do not use the Route from the notebook pod.

== Model Registry

Setup created a Model Registry named **workshop** in `rhoai-model-registries`.

. In OpenShift AI, **Settings → Model resources and operations → Model registry settings**. Confirm **workshop** is listed.
. Open **AI hub → Registry** (label may be *Model registry*). The instance is **empty**. C3 registers the first model here; every later deploy starts from a registered version. Do not deploy from the catalog card in this lab.

Talking points:

* Catalog is discovery. Model Registry is the governed inventory (name, version, artifact URI). Serving pulls the URI the version recorded.
* Model Registry is how platform teams version and share models instead of passing OCI tags in chat.
* This lab uses the **default PostgreSQL (non-production)** database the operator generates. Red Hat does not support that database for production. Production registries use an external PostgreSQL 16.x or MySQL database.

https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5/html/managing_model_registries/creating-a-model-registry_managing-model-registries[Create a model registry]

== MCP Catalog, MCP Registry, and the OpenShift MCP server (Technology Preview)

These three surfaces are **Technology Preview**. They are not supported with Red Hat production SLAs and are not recommended for production.

https://access.redhat.com/support/offerings/techpreview[Technology Preview Features Support Scope]

. **AI hub → MCP servers → Catalog** — browse curated Model Context Protocol servers (Red Hat, partner, community). Confirm the **openshift-mcp-server** card. The Deploy action is live because setup set `mcplifecycleoperator: Managed` and `mcpCatalog: true`.
. **AI hub → MCP servers → Deployments** (this is the MCP Registry surface; flag `mcpRegistry: true`). Select project `{presenter_project}`. Confirm **openshift-mcp-server** is **Available**.
. That instance is the catalog **MCP server for Red Hat OpenShift**. It is **not** the Developer Preview `rhoai-mcp` coding-assistant server.

Talking points:

* The OpenShift MCP server is **read-only** (`core` + `config` toolsets). Its ServiceAccount `mcp-viewer` is bound to ClusterRole `view` (namespaced objects) plus a narrow ClusterRole for core **nodes** (C3b GPU inventory). Built-in `view` cannot list Nodes.
* MCP Catalog / MCP Lifecycle Operator / MCP server for Red Hat OpenShift are Technology Preview. This lab does **not** install MCP Gateway.
* Use this in the show as a catalog + deploy demo. Do not treat it as a production agent runtime.

https://docs.redhat.com/en/documentation/red_hat_openshift_ai_self-managed/3.5/html/working_with_the_mcp_catalog/index[Working with the MCP catalog]
